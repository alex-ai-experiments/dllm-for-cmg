Understanding NLG Metrics for Commit Message Generation

Why BLEU-4 scores are so low, how each metric works, and what BLEU-CODE adds — with real examples from the dLLM ablation study

1. Why Is BLEU So Low?

The Core Problem: Semantic Equivalence ≠ Lexical Overlap

Commit messages are short, semantically dense, and there are many valid ways to express the same change. BLEU measures exact n-gram overlap, so two sentences with the same meaning but different words score near zero.

Real Example from the Dataset

Reference "replace remaining uses of bail"
dLLM "Refactor DAG clear method to include acyclic check and exit condition"
AR "Bail out of infinite loop when clearing DAGs"

The dLLM output is a reasonable commit message — it describes a refactoring of the DAG clearing logic — but shares zero words with the reference. BLEU-4 = 0.0000

The AR baseline at least shares "bail" and gets a marginal boost, but still scores very low because the phrasing is completely different.

Five Reasons BLEU Is Low for Commit Messages

  1. Short references — Labels average ~5-8 words. With BLEU-4, you need matching 4-grams, but a 5-word reference has only two possible 4-grams. One mismatch → score crashes.
  2. Many valid paraphrases — "fix bug in X" vs "resolve issue with X" vs "correct X behavior" all describe the same change but share few n-grams.
  3. Code identifiers — The model may reference BashOperator while the reference says "operators" — semantically equivalent but different tokens.
  4. Style differences — References are often lowercase shorthand ("fix mypy issues") while models generate formal sentences ("Bug fix: Corrected incorrect function signature").
  5. Brevity Penalty is inverted — BLEU penalizes short hypotheses. But here, the generated text is often longer than the reference, so BP=1.0 (no penalty). The problem is low precision — too many extra words dilute matches.

2. How Each Metric Works

BLEU-4 ~0.02

What it measures: Precision of 1- through 4-gram matches between hypothesis and reference, with a brevity penalty.

BLEU = BP × exp( Σ wₙ × log(pₙ) )

pₙ = (clipped n-gram matches) / (total hyp n-grams)
BP = min(1, e^(1 - ref_len/hyp_len))
wₙ = 0.25 for each n ∈ {1,2,3,4}

Why it's low: Requires exact token sequence matches. A 5-word reference has only 2 four-grams. Generated messages use different vocabulary. Smoothing (method1) adds epsilon to zero counts but can't salvage zero overlap.

Range: 0.0 – 1.0 (0 = no overlap, 1 = perfect match)

BLEU-NORM ~0.03

What it measures: Same as BLEU-4 but after normalizing: lowercase + strip all punctuation.

Normalize: "Fix: Bug-fix!" → "fix bugfix"
Then compute BLEU-4 on normalized tokens

Why it helps slightly: Removes case mismatches ("Fix" → "fix") and punctuation noise. Marginal improvement because the core vocabulary mismatch remains.

BLEU-CODE ~0.03

What it measures: BLEU-4 after code-aware tokenization: camelCase splitting, snake_case splitting, and Porter stemming.

"CxfEndpoint" → "cxf endpoint" → stem → "cxf endpoint"
"back_off_factor" → "back off factor" → stem → "back off factor"
"remaining" → stem → "remain"
"removed" → stem → "remov"

Why it helps: Code identifiers like BashOperator become "bash oper" which can partially match "operators" → "oper". Stemming collapses "fixing"/"fixed"/"fix" into "fix".

Still low because: Even with stemming, fundamentally different descriptions ("refactor" vs "replace") don't overlap.

ROUGE-1 ~0.14

What it measures: Unigram overlap between hypothesis and reference, using both precision and recall, reported as F1.

P = (matching unigrams) / (total hyp unigrams)
R = (matching unigrams) / (total ref unigrams)
F1 = 2PR / (P + R)

Why it's higher than BLEU: Only needs single-word matches (not sequences). F1 balances precision and recall, so matching even 1-2 words from a 5-word reference gives nonzero recall. Uses stemming internally.

ROUGE-2 ~0.04

What it measures: Bigram overlap (F1). Needs consecutive 2-word matches.

Same as ROUGE-1 but with bigrams instead of unigrams

Why it's low: Same problem as BLEU — needing consecutive word pairs to match is hard when vocabulary diverges. Slightly better than BLEU-4 because it's only 2-grams (not 4).

ROUGE-L ~0.13

What it measures: Longest Common Subsequence (LCS) based F1. Words don't need to be consecutive — just in the same order.

LCS("fix bug in tests", "fix tests issues")
→ LCS = "fix tests" (length 2, non-consecutive)
P = 2/3, R = 2/4 → F1 = 0.571

Why it's useful: Captures word order similarity even with insertions/deletions. More forgiving than n-gram metrics.

METEOR ~0.10

What it measures: Unigram alignment using exact matches, stems, and WordNet synonyms. Penalizes fragmented matches (word order disruption).

1. Align hyp↔ref via: exact → stem → synonym
2. P = matched/hyp_len, R = matched/ref_len
3. F_mean = 10PR / (R + 9P) [recall-weighted]
4. Penalty = 0.5 × (chunks/matches)³
5. METEOR = F_mean × (1 - Penalty)

Why it's the highest: Synonym matching catches "fix"↔"correct", "remove"↔"delete". Stemming helps with "remaining"→"remain". Recall-weighted, so it rewards covering reference words.

Best for commit messages because it handles paraphrasing better than any other metric here.

CIDEr ~0.5–2.0

What it measures: Corpus-level TF-IDF weighted n-gram cosine similarity. Rewards n-grams that are distinctive (rare across the corpus) and shared between hypothesis and reference.

1. Tokenize hypothesis and reference
2. Build document frequency (DF) from all references in the corpus
3. For each n-gram: TF = count / total_ngrams, IDF = log(N / DF)
4. Build TF-IDF vector for hypothesis and reference
5. CIDEr_n = cosine_similarity(hyp_vec, ref_vec)
6. CIDEr = 10.0 × average(CIDEr_1..CIDEr_4)

Why it matters: Unlike BLEU which treats all n-grams equally, CIDEr down-weights common n-grams (e.g., "fix", "add") and up-weights distinctive ones (e.g., "backoff_factor", "partition sensor"). This better captures whether the model generated the important parts of the commit message.

Scale: Multiplied by 10.0 (convention from the CIDEr paper). Scores typically range from 0 to ~10, with most commit messages scoring 0.5–3.0.

Tokens/sec & Speed Metrics

What they measure: Generation throughput and efficiency.

Tokens/sec = generated_tokens / wall_seconds
Tokens/step = generated_tokens / diffusion_steps
(AR always has tokens/step = 1.0)

Key insight: dLLM generates multiple tokens per step via parallel diffusion, trading quality for speed. Lower confidence threshold → more tokens accepted per step → faster but noisier.

5. BLEU-CODE Deep Dive

How BLEU-CODE Tokenization Differs

BLEU-CODE applies three transformations before computing BLEU-4:

  1. CamelCase splitting: CxfEndpoint → Cxf Endpoint, BashOperator → Bash Operator
  2. snake_case splitting: back_off_factor → back off factor
  3. Porter stemming: remaining → remain, operators → oper, fixing → fix

When BLEU-CODE Helps vs. Doesn't

✓ Helps when:

  • Reference has "operators", generated has "BashOperator" → both stem to "oper"
  • Reference says "fixing", generated says "fixed" → both become "fix"
  • Reference has "retry_config", generated has "retryConfig" → both split + stem similarly

✗ Doesn't help when:

  • Completely different vocabulary ("refactor" vs "replace")
  • Different level of description (high-level vs specific)
  • Synonym usage ("remove" vs "delete" — only METEOR catches this)

7. Key Takeaways

  1. BLEU-4 is a poor metric for commit messages — short references + paraphrasing → near-zero scores for semantically correct outputs.
  2. BLEU-CODE provides ~20-30% relative improvement over BLEU-4 by handling code identifiers and morphological variants, but is still fundamentally limited by the n-gram precision framework.
  3. METEOR is the most informative metric — synonym matching via WordNet and recall-weighted scoring make it best suited for evaluating paraphrased text.
  4. ROUGE-L captures structural similarity — the subsequence-based approach handles word reordering better than strict n-gram metrics.
  5. All metrics agree on the quality-speed trade-off — higher confidence thresholds consistently improve all scores at the cost of throughput.
  6. Semantic similarity metrics (BERTScore, etc.) would likely show much higher scores — these aren't computed here but would be the "right" tool for this task.
